# Customer confirmation implementation

- The confirmation is **only** attempted after a **confirmed successful lead
  delivery** to Sales (Web3Forms returns `success: true`). If lead delivery fails,
  the Worker returns `502` and the confirmation code is never reached.
- **Sender:** `no-reply@mearvaseafood.com` (the `MS_SENDER` binding).
- **Reply-To:** `sales@mearvaseafood.com` — so any customer reply reaches Sales.
- **Recipient:** the buyer (the validated email supplied on the lead).
- **Non-blocking:** the confirmation runs best-effort in the background
  (`ctx.waitUntil`) and is wrapped so that any failure **cannot** affect the lead
  result the customer already received.
- **No false confirmation:** when lead delivery fails, **no** confirmation is sent.
- Content is receipt-only — it acknowledges the enquiry and explicitly states it is
  not a price, availability, freight, or delivery confirmation. No invented data.

- `worker/confirmation.test.mjs`

**What it does:**
- Adds a `logConfirmation(reason, status)` helper that emits **one structured
  line** per confirmation outcome. Each line contains **only**:
  - `event` (always the fixed string `customer_confirmation`),
  - a **sanitized `reason`** (a fixed string literal: `token_failed`,
    `auth_failed`, `no_recipient`, `not_configured`, `sent`, `send_failed`,
    `error`),
  - an **HTTP `status`** code when available.
- **Never** logs access tokens, the client secret, tenant/client IDs, email
  addresses, lead/customer data, or Graph/token response bodies. A dedicated
  log-safety test seeds sensitive values into the environment and asserts none
  appear in any log line.
- Enables Cloudflare Worker **observability** with **persisted logs** in
  `wrangler.toml` (`[observability] enabled = true`), so the confirmation outcome
  is retained and queryable.

# Microsoft Entra and Graph diagnosis

Chronological outcomes (each `customer_confirmation` result drove the next fix):

1. **`token_failed` + `400`** — the Microsoft token endpoint rejected the
   client-credentials request. Root cause: an **incorrect `MS_TENANT_ID`** had been
   entered. The incorrect value (beginning `84f…`) was actually an Entra
   **Secret ID**, not the tenant id.
2. **Correct tenant id configured** through the **Wrangler versions-secret
   workflow** (`wrangler versions secret put MS_TENANT_ID`, then
   `wrangler versions deploy …@100%`) — a secret-only change with no code
   deployment.
3. **`token_failed` + `401`** afterward — this proved the **tenant was now valid**
   (the request reached authentication) and **isolated the failure to the client
   credential** (invalid client secret).
4. **A new Entra client secret was created.** Only the Entra secret **Value** is
   valid for `MS_CLIENT_SECRET`; the **Secret ID must never be used**.
5. A **Cloudflare dashboard edit** of the client secret produced a serving Worker
   version in which **`MS_CLIENT_SECRET` was missing** entirely — which surfaced as
   **`not_configured`** at runtime (the `m365Configured` guard failed before any
   Microsoft call).
6. **`MS_CLIENT_SECRET` was restored safely** through the **Wrangler versions-secret
   workflow**, and the resulting version was rolled out to 100%.
